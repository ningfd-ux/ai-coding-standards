# React Context Organization Standards

Well-organized React Context providers make global state predictable for both developers and AI coding tools. Consistent patterns for context structure reduce bugs, improve autocomplete, and make state logic auditable.

---

## Why Context Organization Matters

Poorly organized context leads to:

- Providers that re-render the entire tree unnecessarily
- Context files that grow into unreadable monoliths
- Mixed concerns (data fetching + state + UI logic in one context)
- AI tools generating incorrect context consumption patterns
- Debugging nightmares when multiple contexts interact unpredictably

A clear context organization strategy keeps state logic clean, testable, and AI-friendly.

---

## File Structure Pattern

### One File Per Context

Each context gets its own file. Name by domain, not by technical role.

```tsx
src/
  contexts/
    AuthContext.tsx
    ThemeContext.tsx
    CartContext.tsx
    NotificationContext.tsx
```

### Avoid Monolithic State Files

```
// Incorrect - everything in one file
src/
  contexts/
    AppContext.tsx        // 500+ lines, all state
```

## Context Module Structure

Every context file follows the same internal structure. This consistency helps AI tools predict where to find and modify code.

```tsx
// === 1. Types & Interfaces ===
interface AuthState {
  user: User | null
  isAuthenticated: boolean
  isLoading: boolean
}

type AuthAction =
  | { type: 'LOGIN_START' }
  | { type: 'LOGIN_SUCCESS'; payload: User }
  | { type: 'LOGIN_ERROR'; payload: string }
  | { type: 'LOGOUT' }

// === 2. Context Definition ===
interface AuthContextValue {
  state: AuthState
  login: (email: string, password: string) => Promise<void>
  logout: () => void
}

const AuthContext = createContext<AuthContextValue | undefined>(undefined)

// === 3. Reducer (if using useReducer) ===
function authReducer(state: AuthState, action: AuthAction): AuthState {
  switch (action.type) {
    case 'LOGIN_START':
      return { ...state, isLoading: true }
    case 'LOGIN_SUCCESS':
      return { user: action.payload, isAuthenticated: true, isLoading: false }
    case 'LOGIN_ERROR':
      return { ...state, isLoading: false }
    case 'LOGOUT':
      return { user: null, isAuthenticated: false, isLoading: false }
    default:
      return state
  }
}

// === 4. Provider Component ===
export function AuthProvider({ children }: { children: React.ReactNode }) {
  const [state, dispatch] = useReducer(authReducer, {
    user: null,
    isAuthenticated: false,
    isLoading: false,
  })

  const login = useCallback(async (email: string, password: string) => {
    dispatch({ type: 'LOGIN_START' })
    try {
      const user = await api.login(email, password)
      dispatch({ type: 'LOGIN_SUCCESS', payload: user })
    } catch (error) {
      dispatch({ type: 'LOGIN_ERROR', payload: (error as Error).message })
    }
  }, [])

  const logout = useCallback(() => {
    dispatch({ type: 'LOGOUT' })
  }, [])

  const value = useMemo(
    () => ({ state, login, logout }),
    [state, login, logout]
  )

  return <AuthContext.Provider value={value}>{children}</AuthContext.Provider>
}

// === 5. Custom Hook ===
export function useAuth(): AuthContextValue {
  const context = useContext(AuthContext)
  if (!context) {
    throw new Error('useAuth must be used within an AuthProvider')
  }
  return context
}
```

### Commented Section Headers

Use consistent section markers in every context file. This creates predictable anchor points for AI code editing.

```tsx
// Types & Interfaces ----------
// Context Definition ----------
// Reducer ---------------------
// Provider Component ----------
// Custom Hook -----------------
```

## State + Actions Separation

### Separate State Shape from Actions

Define state interfaces and action types separately. This makes reducers type-safe and AI autocomplete accurate.

```tsx
// Correct - clear separation
interface NotificationState {
  items: Notification[]
  unreadCount: number
}

type NotificationAction =
  | { type: 'ADD'; payload: Notification }
  | { type: 'DISMISS'; payload: string }
  | { type: 'MARK_READ'; payload: string }
  | { type: 'CLEAR_ALL' }

// Incorrect - mixed concerns
interface NotificationContextType {
  items: Notification[]
  addNotification: (n: Notification) => void
  dismissNotification: (id: string) => void
  state: { items: Notification[] }
}
```

## Provider Composition

### Nest Providers by Dependency Order

Providers that depend on other providers must be nested in dependency order.

```tsx
// Correct - dependency order
function AppProviders({ children }: { children: React.ReactNode }) {
  return (
    <AuthProvider>
      <ThemeProvider>
        <NotificationProvider>
          <CartProvider>
            {children}
          </CartProvider>
        </NotificationProvider>
      </ThemeProvider>
    </AuthProvider>
  )
}

// Correct - flattened composition
function AppProviders({ children }: { children: React.ReactNode }) {
  return (
    <Compose providers={[AuthProvider, ThemeProvider, NotificationProvider, CartProvider]}>
      {children}
    </Compose>
  )
}
```

### Avoid Provider Chains in Root

Do not dump all providers in the root layout file. Create a dedicated provider composition component.

```tsx
// Incorrect - cluttered root
export default function RootLayout({ children }: { children: React.ReactNode }) {
  return (
    <AuthProvider>
      <ThemeProvider>
        <NotificationProvider>
          ...
        </NotificationProvider>
      </ThemeProvider>
    </AuthProvider>
  )
}

// Correct - clean root
export default function RootLayout({ children }: { children: React.ReactNode }) {
  return <AppProviders>{children}</AppProviders>
}
```

## Context Value Memoization

### Always Memoize Context Values

Without memoization, every context consumer re-renders on every provider render.

```tsx
// Correct - memoized value
export function AuthProvider({ children }: { children: React.ReactNode }) {
  const [state, dispatch] = useReducer(authReducer, initialState)

  const login = useCallback(async (...) => { ... }, [])
  const logout = useCallback(() => { ... }, [])

  const value = useMemo(
    () => ({ state, login, logout }),
    [state, login, logout]
  )

  return <AuthContext.Provider value={value}>{children}</AuthContext.Provider>
}

// Incorrect - new object every render
export function AuthProvider({ children }: { children: React.ReactNode }) {
  const [state, dispatch] = useReducer(authReducer, initialState)
  return (
    <AuthContext.Provider value={{ state, login, logout }}>
      {children}
    </AuthContext.Provider>
  )
}
```

### Split Contexts for Performance

When a context has frequently-changing and rarely-changing values, split them.

```tsx
// Correct - split by update frequency
const AuthStateContext = createContext<AuthState | undefined>(undefined)
const AuthActionsContext = createContext<AuthActions | undefined>(undefined)

export function AuthProvider({ children }: { children: React.ReactNode }) {
  const [state, dispatch] = useReducer(authReducer, initialState)
  const actions = useMemo(() => ({
    login: (email: string, password: string) => { ... },
    logout: () => { ... },
  }), [])

  return (
    <AuthStateContext.Provider value={state}>
      <AuthActionsContext.Provider value={actions}>
        {children}
      </AuthActionsContext.Provider>
    </AuthStateContext.Provider>
  )
}
```

## Custom Hook Patterns

### Custom Hooks Are the Public API

Consumers should never use `useContext` directly. Always wrap context consumption in a custom hook.

```tsx
// Correct - exported custom hook
export function useAuth(): AuthContextValue {
  const context = useContext(AuthContext)
  if (!context) {
    throw new Error('useAuth must be used within an AuthProvider')
  }
  return context
}

// Usage
function UserProfile() {
  const { state, login } = useAuth()
  // ...
}

// Incorrect - raw useContext in components
function UserProfile() {
  const auth = useContext(AuthContext)
  // ...
}
```

### Guard Hook with Error

Every context hook should throw a meaningful error when used outside its provider.

```tsx
export function useTheme(): ThemeContextValue {
  const context = useContext(ThemeContext)
  if (!context) {
    throw new Error('useTheme must be used within a ThemeProvider. ' +
      'Wrap your component tree with <ThemeProvider>.')
  }
  return context
}
```

## Common Mistakes

- **No memoization** - context values that recreate on every render cause infinite re-renders
- **Monolithic context files** - one context mixing auth, theme, notifications, and cart
- **Missing error guards** - custom hooks that silently return undefined outside provider
- **Raw useContext in components** - couples components to context implementation
- **Over-splitting** - 15 tiny contexts are worse than 3 well-organized ones
- **Undefined initial state** - context state that starts as null or undefined everywhere

## AI Coding Prompt Example

```
When organizing React Context in this project:
- Use one file per context with 5 sections: Types, Context, Reducer, Provider, Hook
- Keep context values memoized with useMemo and useCallback
- Export a custom hook (useXxx) instead of exposing useContext directly
- Guard custom hooks with a check that throws if used outside provider
- Separate state from actions using split contexts for performance
- Create a dedicated AppProviders composition component for nesting
- Use useReducer for complex state, useState for simple values
- Name context files by domain: AuthContext.tsx, ThemeContext.tsx
```

---

## Best Practices Summary

- One file per context with consistent section structure
- Always memoize context values (useMemo + useCallback)
- Export custom hooks as the public API, not raw context
- Guard hooks with provider-check error messages
- Split fast-changing state from stable actions
- Compose providers in a dedicated component, not the root layout
- Use useReducer for complex state logic, useState for simple values
- Keep contexts domain-focused -- avoid kitchen-sink providers
