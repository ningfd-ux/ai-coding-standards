# React Component Structure Standards

Well-structured React components produce more predictable AI-generated code and are easier to maintain at scale.

---

## Why Component Structure Matters

Poor component structure leads to:

- AI tools generating inconsistent component patterns
- Props drilling that becomes unmanageable
- Duplicate logic spread across files
- Difficult onboarding for new developers
- Components that are hard to test in isolation

A clear structure gives AI tools a predictable template to follow.

---

## File Organization

One component per file. Co-locate related files.

### Correct ✅

```
components/
├── UserCard/
│   ├── UserCard.tsx
│   ├── UserCard.test.tsx
│   └── UserCard.module.css
```

### Incorrect ❌

```
components/
├── UserCard.tsx        // component, styles, and types all in one
├── UserList.tsx
├── AllStyles.css       // global styles mixed together
```

### With Barrel Exports

```
components/
└── UserCard/
    ├── UserCard.tsx
    ├── UserCard.test.tsx
    ├── UserCard.module.css
    └── index.ts              // re-export for clean imports
```

```ts
// index.ts
export { UserCard } from './UserCard'
export type { UserCardProps } from './UserCard'
```

Usage:
```ts
import { UserCard } from '@/components/UserCard'
```

## Component Declaration

Use named function declarations, not arrow functions or default exports.

### Correct ✅

```tsx
interface UserCardProps {
  name: string
  role: string
  avatarUrl?: string
}

export function UserCard({ name, role, avatarUrl }: UserCardProps) {
  return (
    <div className="rounded-lg border p-4">
      <h3>{name}</h3>
      <p>{role}</p>
    </div>
  )
}
```

### Incorrect ❌

```tsx
export default ({ name, role }) => {
  return <div>{name}</div>
}
```

## Props Design

Keep props interfaces focused. Use discriminated unions for variants.

### Correct ✅

```tsx
interface ButtonBaseProps {
  size?: 'sm' | 'md' | 'lg'
  disabled?: boolean
}

interface PrimaryButtonProps extends ButtonBaseProps {
  variant: 'primary'
  onClick: () => void
}

interface LinkButtonProps extends ButtonBaseProps {
  variant: 'link'
  href: string
}

type ButtonProps = PrimaryButtonProps | LinkButtonProps

export function Button(props: ButtonProps) {
  // ...
}
```

### Incorrect ❌

```tsx
interface ButtonProps {
  variant?: string
  onClick?: () => void
  href?: string
  // unclear which props are needed when
}
```

## Component Composition

Prefer composition over prop proliferation.

### Correct ✅

```tsx
export function Card({ children }: { children: React.ReactNode }) {
  return <div className="rounded-lg border">{children}</div>
}

Card.Header = function CardHeader({ children }: { children: React.ReactNode }) {
  return <div className="border-b px-4 py-3">{children}</div>
}

Card.Body = function CardBody({ children }: { children: React.ReactNode }) {
  return <div className="p-4">{children}</div>
}
```

Usage:
```tsx
<Card>
  <Card.Header>Title</Card.Header>
  <Card.Body>Content</Card.Body>
</Card>
```

### Incorrect ❌

```tsx
export function Card({
  header,
  body,
  footer,
  headerClassName,
  bodyClassName,
}: CardProps) {
  // 10+ props that could be composition
}
```

## Server & Client Components (React 19 / Next.js App Router)

Use `'use client'` boundaries intentionally. Keep server components as the default.

### Correct ✅

```tsx
// UserProfile.tsx — Server Component (default)
import { db } from '@/lib/db'
import { UserAvatar } from './UserAvatar' // client component

export function UserProfile({ userId }: { userId: string }) {
  const user = await db.user.findUnique(userId) // direct DB access
  return (
    <div>
      <h1>{user.name}</h1>
      <UserAvatar user={user} /> {/* client island */}
    </div>
  )
}
```

```tsx
// UserAvatar.tsx — Client Component
'use client'

import { useState } from 'react'

export function UserAvatar({ user }: { user: { name: string; avatarUrl?: string } }) {
  const [isOpen, setIsOpen] = useState(false)
  // ...
}
```

### Incorrect ❌

```tsx
// Everything as client component = bundle bloat
'use client'
import { useEffect, useState } from 'react'
import { db } from '@/lib/db'  // server-only import in client component

export function UserProfile({ userId }: { userId: string }) {
  // ...
}
```

## State Management

Keep state as close to where it's used as possible. Lift only when needed.

### Correct ✅

```tsx
export function SearchInput() {
  const [query, setQuery] = useState('')

  return (
    <input
      value={query}
      onChange={(e) => setQuery(e.target.value)}
      placeholder="Search..."
    />
  )
}
```

### Incorrect ❌

```tsx
// Lifting state to parent when SearchInput is the only consumer
export function Page() {
  const [query, setQuery] = useState('')
  return <SearchInput query={query} setQuery={setQuery} />
}
```

### Using React 19 Hooks

```tsx
import { use, useActionState, useOptimistic } from 'react'

// use() for reading async resources
export function Comments({ commentsPromise }: { commentsPromise: Promise<Comment[]> }) {
  const comments = use(commentsPromise)
  return comments.map(c => <Comment key={c.id} comment={c} />)
}

// useActionState for form handling
export function LikeButton({ postId }: { postId: string }) {
  const [likes, formAction, isPending] = useActionState(
    async (previousLikes: number) => {
      const res = await fetch(`/api/posts/${postId}/like`, { method: 'POST' })
      return res.json().likes
    },
    0
  )
  return (
    <form action={formAction}>
      <button type="submit" disabled={isPending}>
        {likes} {isPending ? '...' : 'Likes'}
      </button>
    </form>
  )
}
```

## Event Handlers

Prefix handlers with `handle`. Props callbacks with `on`.

### Correct ✅

```tsx
export function Form({ onSubmit }: { onSubmit: (data: FormData) => void }) {
  const handleSubmit = (e: React.FormEvent) => {
    e.preventDefault()
    // ...
    onSubmit(data)
  }

  return <form onSubmit={handleSubmit}>...</form>
}
```

## Error Boundaries

Wrap error-prone sections in error boundary components.

```tsx
'use client'

import { Component, type ReactNode } from 'react'

interface ErrorBoundaryProps {
  fallback?: ReactNode
  children: ReactNode
}

interface ErrorBoundaryState {
  hasError: boolean
}

export class ErrorBoundary extends Component<ErrorBoundaryProps, ErrorBoundaryState> {
  state = { hasError: false }

  static getDerivedStateFromError(): ErrorBoundaryState {
    return { hasError: true }
  }

  render() {
    if (this.state.hasError) {
      return this.props.fallback ?? <div>Something went wrong</div>
    }
    return this.props.children
  }
}
```

## AI Coding Prompt Example

```
When generating React components:

- Named function declarations with explicit Props interfaces — no default exports
- One component per file, co-locate test (.test.tsx) and style (.module.css) files
- Prefer composition (compound components) over prop proliferation
- Keep state local, lift only when shared
- Prefix handlers with "handle", callback props with "on"
- Use discriminated unions for component variants
- Default to Server Components; add 'use client' only when necessary (hooks, state, events)
- Use React 19 patterns: use() for promises, useActionState for forms, useOptimistic for optimistic updates
- Wrap error-prone UI sections in ErrorBoundary
- Barrel exports (index.ts) for clean import paths
```

## FAQ

**Q: Should I use default exports or named exports?**
A: Named exports. They enable better tree-shaking, consistent imports, and explicit autocomplete. Default exports cause import naming inconsistencies across the codebase.

**Q: When should I add `'use client'`?**
A: Only when you need React hooks (useState, useEffect, useContext), browser APIs, event handlers, or interactive state. Everything else should be a Server Component by default.

**Q: What's the difference between React 19 `use()` and `useEffect` for data fetching?**
A: `use()` integrates with Suspense natively — the parent controls the loading state. `useEffect` requires manual loading state management. Use `use()` for async data your component depends on, `useEffect` for side effects.

**Q: Should I put PropTypes alongside TypeScript interfaces?**
A: No. With TypeScript, PropTypes are redundant. TypeScript provides compile-time checking; PropTypes only adds runtime overhead and bundle size.

**Q: How do I handle global state?**
A: Start with React context + useReducer for simple cases. Lift to Zustand or Jotai when context causes excessive re-renders. Avoid Redux for new projects unless you have specific middleware/ecosystem needs.

## Best Practices Summary

- Named exports, one component per file
- Explicit TypeScript interfaces for all props
- Compound components for complex UIs
- State as local as possible
- Consistent event handler naming
- Server Components by default, `'use client'` only when needed
- React 19 hooks for async and form state
- Error boundaries for resilience
- Barrel exports for clean imports
