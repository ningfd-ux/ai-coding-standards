# TypeScript Naming Conventions

Consistent naming conventions improve code readability, maintainability, and AI-assisted code generation quality.

AI coding tools perform significantly better when variable names, interfaces, components, and functions follow predictable patterns.

---

## Why Naming Consistency Matters

Inconsistent naming creates problems such as:

- Reduced readability
- Harder refactoring
- Confusing AI-generated code
- Duplicate abstractions
- Poor autocomplete experience

Consistent naming standards help both developers and AI tools understand project structure more effectively.

---

## General Naming Principles

Follow these rules across the codebase:

- Prefer descriptive names over short abbreviations
- Use consistent casing for each symbol type
- Avoid unnecessary prefixes (like `I` for interfaces)
- Keep names predictable and intention-revealing
- Align file names with exported symbols

---

## Variable Naming

Use camelCase for variables and functions.

### Correct ✅

```ts
const userProfile = {}
const isAuthenticated = true

function fetchUserData() {}
```

### Incorrect ❌

```ts
const User_Profile = {}
const auth = true

function GetUser() {}
```

### Boolean Convention

Use `is`, `has`, `can`, `should`, `will` prefixes for booleans:

```ts
const isSubscribed = true
const hasPermission = false
const canEdit = user.role === 'editor'
```

---

## Component Naming

Use PascalCase for React components.

### Correct ✅

```tsx
export function UserCard() {}
export function SettingsModal() {}
export function ProfileDropdownMenu() {}
```

### Incorrect ❌

```tsx
export function userCard() {}
export function settings_modal() {}
export function Profile_dropdown_Menu() {}
```

---

## React Hook Naming

Prefix custom hooks with `use`. Return an array or a named object.

### Correct ✅

```ts
function useUser(userId: string): { user: User | null; isLoading: boolean; error: Error | null } {
  // ...
}

function useForm<T>(initial: T): [T, (patch: Partial<T>) => void] {
  // ...
}
```

### Incorrect ❌

```ts
function fetchUser(userId: string) {
  // looks like a regular function, breaks hooks rules
}
```

## Interface Naming

Avoid the `I` prefix for interfaces. Use PascalCase.

### Correct ✅

```ts
interface User {
  id: string
  name: string
  email: string
}

interface AuthResponse {
  token: string
  expiresAt: number
}
```

### Incorrect ❌

```ts
interface IUser {
  id: string
}

interface IAuthResponse {
  token: string
}
```

### When to Use Interface vs Type

```ts
// Interface — prefer for public API shapes (can be extended)
interface UserPreferences {
  theme: 'light' | 'dark'
  language: string
}

// Type — prefer for unions, intersections, and computed types
type Status = 'idle' | 'loading' | 'success' | 'error'
type ApiResult<T> = { data: T } | { error: string }
type ComponentProps = ButtonProps & { className?: string }
```

---

## Type Alias Naming

Use PascalCase for type aliases.

### Correct ✅

```ts
type UserRole = 'admin' | 'editor' | 'viewer'
type ApiResponse<T> = { data: T; error: null }
type ValueOf<T> = T[keyof T]
```

### Incorrect ❌

```ts
type userRole = 'admin' | 'editor'
type api_response<T> = { data: T }
```

---

## Enum Naming

Use PascalCase for enum names and enum members.

### Correct ✅

```ts
enum UserRole {
  Admin,
  Editor,
  Viewer,
}
```

### Incorrect ❌

```ts
enum user_role {
  admin,
  editor,
}
```

### Prefer String Enums

```ts
enum HttpStatus {
  Ok = 'OK',
  NotFound = 'NOT_FOUND',
  InternalError = 'INTERNAL_ERROR',
}
```

## Generic Type Parameters

Use descriptive generic names for complex cases. Single letters for simple cases.

### Correct ✅

```ts
// Simple: single letter
function identity<T>(value: T): T

// Complex: descriptive
function createPair<TKey, TValue>(key: TKey, value: TValue): [TKey, TValue]
function mergeObjects<TObjectA, TObjectB>(a: TObjectA, b: TObjectB): TObjectA & TObjectB
```

### Incorrect ❌

```ts
function process<T, U, V>(a: T, b: U, c: V)  // meaningless when >2 params
```

## File Naming Standards

Use kebab-case for filenames.

### Correct ✅

```
user-profile.ts
auth-service.ts
settings-modal.tsx
use-auth.ts
```

### Incorrect ❌

```
UserProfile.ts
AuthService.ts
settingsModal.tsx
useAuth.ts
```

---

## Constants

Use UPPER_SNAKE_CASE for module-level constants.

### Correct ✅

```ts
const MAX_RETRY_COUNT = 3
const API_BASE_URL = 'https://api.example.com'
const DEFAULT_PAGE_SIZE = 20
```

### Incorrect ❌

```ts
const maxRetryCount = 3
const apiBaseUrl = 'https://api.example.com'
```

## Modern TypeScript Patterns (TS 5.x)

### `satisfies` for Type Validation Without Widening

```ts
const palette = {
  red: [255, 0, 0],
  green: '#00ff00',
  blue: [0, 0, 255],
} satisfies Record<string, string | number[]>

// palette.red is type number[], not string | number[]
// palette.green is type string
```

### `const` Type Parameters

```ts
function asConst<T extends readonly string[]>(arr: T): T {
  return arr
}

const roles = asConst(['admin', 'editor', 'viewer'])
// type: readonly ["admin", "editor", "viewer"], not string[]
```

```
- UPPER_SNAKE_CASE for module-level constants
- Interface for public API shapes (extensible), type for unions/computed types
- Use satisfies for type validation without widening
- Descriptive generics when more than 2 type parameters
- Prefer string enums over numeric enums
```

## FAQ

**Q: Why avoid the `I` prefix for interfaces?**
A: The `I` prefix is a C#/Java convention that adds noise without value in TypeScript. TypeScript is structurally typed — there is no runtime distinction between interface and class. `User` is cleaner than `IUser`, and if you later change from interface to class, you don't need to rename.

**Q: When should I use `interface` vs `type`?**
A: Use `interface` for object shapes that may be extended (declaration merging). Use `type` for unions, intersections, mapped types, and computed types. For simple component props, both work — pick one and stay consistent.

**Q: How do I name files that export multiple things?**
A: File names should match the primary export. If a file exports `UserCard` as the main component, name it `user-card.tsx`. Barrel exports in `index.ts` can re-export multiple things from a directory.

**Q: What about naming in tests?**
A: Test files mirror their source: `user-card.test.tsx` for `user-card.tsx`. Test descriptions use sentence case: `describe('UserCard', () => { it('renders user name', () => { ... }) })`.

**Q: Should I use `const enum` or regular `enum`?**
A: Avoid `const enum` — it can cause issues with bundlers and isolatedModules. Use regular `enum` or `as const` objects instead.

## Best Practices Summary

- Use descriptive, intention-revealing names
- Keep casing consistent per symbol type
- Align filenames with exports
- Avoid abbreviations unless universally understood
- Prefer predictable patterns across the repository
- Avoid I-prefix interfaces
- Use satisfies for precise type inference
- Descriptive generics for complex type parameters
